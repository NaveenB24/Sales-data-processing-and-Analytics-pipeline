1 · What this project is

The brief asked for a full-stack system that ingests bulk sales data, processes it concurrently, computes analytical metrics, and presents them on a live dashboard — fully self-contained, with no external APIs.

1.1 The seven requirements, and where each one lives

RequirementWhere it is implementedWhat it does
1. Authentication & usersapp/routers/auth.py
app/security.py		 Signup and login with bcrypt-hashed passwords and JWTs. Users only ever see their own jobs. Role-based admin access is included.
2. Upload & processingapp/routers/jobs.py
app/processing/validation.py		 CSV and JSON upload, per-row validation with named error codes, derived net_amount, and a simulated per-row cost so concurrency matters.
3. Aggregation & mathapp/processing/metrics.py Revenue totals and breakdowns, average, median, standard deviation with a variance flag, top 5, daily and monthly trends, discount impact.

6. UI / dashboardfrontend/src/ Upload with live progress, job summaries, three chart types, top-5 table, row explorer, annotated export.
7. Logging & observabilityapp/logging_config.py
app/routers/admin.py		 Structured JSON logs with levels, a correlation ID per job, and a metrics endpoint with failure rate and timing.

1.2 Bonus items that were also built

Role-based access

The first account registered becomes an administrator and gains a system-wide view of users, jobs and metrics.

Background job queue

Uploads return immediately; a dispatcher thread runs jobs and publishes live progress.

WebSocket live updates

Progress streams over a socket, with automatic polling fallback if the socket cannot open.

Structured JSON logging

Machine-readable log lines with levels and correlation IDs for tracing a job across threads.

Rate limiting & retries

Per-user upload throttling; transient row failures are retried with backoff before being demoted.

CI/CD & Docker

GitHub Actions runs tests, type-checks and image builds. Docker Compose brings the whole stack up.

1.3 What was deliberately not built

Redis, Celery, Postgres and a scheduled-email reporter were all considered and left out. Section 13 explains why in each case, and Section 15 states the limits that choice creates. The short version: the brief rewards a system that runs anywhere with no setup, and every omitted piece sits behind a narrow interface so it can be swapped in later without touching the rest of the code.

2 · Running it on your machine

You need Python 3.12 or newer and Node.js 20 or newer. Nothing else — no database server, no Redis, no Docker (unless you want it).

2.1 The three-command path

git clone <repository-url> sales-data-processor
cd sales-data-processor

./scripts/setup.sh     # creates the Python virtualenv, installs backend + frontend packages
./scripts/dev.sh       # starts the API on :8000 and the dashboard on :5173

Then open http://localhost:5173 in a browser. Create an account, and upload sample_data/sample_sales.csv — the seven-row file from the brief.

4 · How it works, end to end

Follow one uploaded file from the browser to the chart that renders it.

The system in one picture. Everything inside the outer boxes runs in a single Python process; the database is one file on disk.

4.1 The seven steps

#StepWhat happens
1UploadThe file streams to disk in 1 MB chunks, with the size cap checked while writing so an oversized file never fully lands. A job row is created in pending and stamped with a correlation ID. A per-user rate limiter guards the endpoint.
2QueueThe job id goes onto the queue — automatically if "process on upload" is ticked, or later when the user presses Process. A background dispatcher thread pulls ids one at a time.
3ProcessThe file is streamed and its rows handed to a pool of worker threads in bounded batches. Each row pays a small simulated processing cost, then gets validated. A row whose processing throws is retried with backoff.
4De-duplicateWorkers finish out of order, so duplicates are not detected inside them. Each completed batch is re-sorted by row number and passed through the duplicate tracker on a single thread. Same file in, same answer out, every time.
5PersistRows are bulk-inserted in chunks. The job's counters advance as batches land, and a progress event is published every 25 rows.
6AggregateThe stored rows are streamed back and the metrics computed, then written as six report records — one per metric family. Keeping this separate from row processing is what makes "re-run aggregation" cheap and independent.
7DeliverThe dashboard reads the report for its charts and the rows endpoint for the explorer. Export re-streams the rows as annotated CSV or JSON.
Nothing in a bad file can crash the pipeline. A malformed row becomes an invalid row carrying an error code. Only an unreadable file fails the job — and that marks it failed with a message while the API keeps serving everyone else.

5 · The concurrency model

The brief requires that row validation runs concurrently rather than sequentially. This section explains what was built and why each choice was made.

5.1 Two levels of parallelism

There are two separate questions — how many jobs run at once, and how many rows within a job run at once. They get different answers.

Jobs: one at a time

A single dispatcher thread pulls job ids off the queue and runs them in sequence. SQLite permits one writer at a time, so running several write-heavy jobs concurrently would just produce lock contention and retries.

The user never waits for this: the upload returns immediately and the job runs behind them.

Rows: eight at a time

Inside each job, a pool of worker threads validates rows in parallel. This is where the brief's concurrency requirement is met, and where the measurable speedup comes from.

The pool size is configurable via WORKER_POOL_SIZE.

5.2 Why threads rather than async or processes

The simulated per-row cost is a sleep, which is I/O-shaped, and the real work — parsing, arithmetic, validation — is short. Threads therefore give genuine wall-clock speedup without process-spawn cost, without pickling rows between processes, and without rewriting the synchronous database layer as async. If row processing ever became genuinely CPU-bound, swapping ThreadPoolExecutor for ProcessPoolExecutor is a change contained to one module.

5.3 The measured result

ScenarioSequential would takeActualWhere it is proven
120 rows at 25 ms each, pool of 83.00 s0.39 stest_concurrency.py
10,000 rows at 2 ms each, pool of 820.0 s~3.8 stest_scale.py, and observed live

The concurrency test asserts a hard upper bound on wall-clock time, so if someone silently makes the pipeline sequential again, the suite fails rather than quietly getting slower.

5.4 Keeping the output deterministic

Parallelism creates a trap: if duplicate detection ran inside the workers, which row got marked as the original would depend on which thread happened to finish first. The same file could produce different reports on different runs.

The fix is to split the work. Validation — which is pure and order-independent — runs in parallel. Duplicate detection — which is inherently order-dependent — runs single-threaded, over each completed batch, in row-number order. Slightly more code; completely reproducible output.

5.5 Keeping memory bounded

Three separate mechanisms stop a large file from being held in memory at once: the parser streams rows rather than reading the file into a list, at most 2,000 futures are in flight at a time, and rows are inserted in chunks of 1,000. Reading back for aggregation and export uses streaming cursors. A 10,000-row file was verified end to end; the same code path handles far larger files at constant memory.

5.6 Retry behaviour

If processing a row raises an unexpected exception, it is retried twice with a short backoff. If it still fails, that row is marked invalid with the code PROCESSING_ERROR and the job carries on. One poisonous row cannot take down a 10,000-row import.

6 · The data model

Four tables in one SQLite file. Every index exists because a specific query needs it, not by reflex.

6.1 The tables

6.3 SQLite configuration

The database opens with four settings that matter for this workload:

SettingWhy
journal_mode = WALReaders never block on the writer, so the dashboard stays responsive while a job writes rows.
synchronous = NORMALThe usual durability-for-throughput trade for an analytics workload.
foreign_keys = ONDeleting a job genuinely cascades to its rows and reports.
busy_timeout = 30000Brief write contention waits rather than failing.

6.4 Moving to PostgreSQL

Change DATABASE_URL. Nothing in the application code assumes SQLite — the engine builder applies the SQLite-specific settings only when the URL says SQLite, and everything else goes through SQLAlchemy. The one thing a production move would add is a migration tool; the schema is currently created directly from the models, which is fine for a greenfield database but would need Alembic once there is data worth preserving.

7.2 Duplicates — and a conflict in the brief

The brief contradicts itself here, and the resolution matters. It asks for "duplicate transaction_ids flagged". But its own sample file describes TXN-1005 as "a duplicate of TXN-1001" — and those two IDs are different. Only the row contents repeat. Implementing the stated rule literally would have failed the brief's own acceptance note.

Both signals are therefore implemented:

CodeMeaning
DUPLICATE_IDThe same transaction_id appears again — the same record submitted twice.
DUPLICATE_RECORDA fresh ID, but every other field matches an earlier row — the same sale re-submitted under a new ID.

In both cases the first occurrence stays valid and the repeat is marked duplicate, with its money fields cleared so a repeated transaction can never inflate revenue.

The cost of this choice: content matching could in principle flag two genuinely separate sales that happen to agree on region, category, quantity, price, discount and date. That is a real false-positive risk, so it is configurable — setting DUPLICATE_DETECTION=id restores strict ID-only matching. The default honours the brief.

7.3 Derived values

gross_amount    = quantity × unit_price
discount_amount = gross_amount × (discount_percent ÷ 100)
net_amount      = gross_amount − discount_amount

Computed only for valid rows, and rounded to two decimals when stored.

7.4 The metrics computed per job

Revenue

Total (sum of net amounts), gross, and the breakdown by region and by product category with each one's share of the total.

Averages

Average order value, median transaction value, and the minimum and maximum.

Spread

Sample standard deviation, plus a variance flag raised when the coefficient of variation exceeds 1.0 — the signal that the average is a poor summary.

Discount impact

Total revenue given away to discounts, and what percentage of gross revenue that represents.

Trends

Revenue per day and per month, each with the percentage change against the previous period.

Top transactions

The five highest-value transactions, by net amount.

9 · The dashboard

Five screens. Every screenshot here is of the real application running against the real backend, not a mockup.

9.1 Live progress, and what happens when the socket fails

While a job runs, the dashboard opens a WebSocket to /ws/jobs/{id} and receives an event roughly every 25 rows. The progress bar, row counter and valid/invalid/duplicate tallies all update from those events.

WebSockets do not survive every corporate proxy. If the socket fails to open within three seconds, or closes abnormally, the hook transparently switches to polling the progress endpoint every two seconds and the indicator changes from "live" to "polling". The user still sees progress; only the update frequency changes.

9.2 Design and accessibility

A real design system

Hand-written CSS with custom properties for colour, spacing, radius and type. No UI kit, no Tailwind — four runtime dependencies in total.

Light and dark

Both themes are first-class and follow the operating system preference. The charts read the same tokens, so they re-colour with the rest of the page.

Responsive

Verified down to 390 px with zero horizontal overflow on every route: cards stack, tables scroll within their own region, the nav collapses.

Accessible

Semantic landmarks, a skip link, labelled controls, visible focus rings, live regions for progress and toasts, and status conveyed by text as well as colour.

9.3 Every async surface handles four states

Loading, empty, error and loaded. An empty dashboard explains what to do next rather than showing a blank table; a failed request shows what went wrong with a retry button rather than an indefinite spinner.

10 · Observability

When something goes wrong at three in the morning, the question is always the same: what actually happened? These are the answers the system can give.

10.1 Structured logs

Every log line is a single JSON object, written both to standard output and to backend/logs/app.log. Machine-readable means greppable, and means a log shipper can consume it without parsing rules.

{"event": "job.completed", "job_id": "7912d1d8-…", "total_rows": 10000,
 "valid_rows": 9383, "invalid_rows": 407, "duplicate_rows": 210,
 "duration_ms": 3751.4, "avg_row_ms": 0.375,
 "correlation_id": "fc89e79a-…", "level": "info",
 "timestamp": "2026-10-02T11:04:12.882Z"}

10.2 Correlation IDs

This is the part that makes the logs genuinely useful. Each job is stamped with a correlation ID at upload. Every subsequent log line — from the queue, from the worker threads, from aggregation — carries that same ID. Separately, each HTTP request gets its own ID, returned in the X-Correlation-ID response header and accepted from the caller if supplied.

The job's correlation ID is shown on the job detail page, so a user reporting a problem can read it off the screen, and you can retrieve the entire history of that job with one command:

grep fc89e79a backend/logs/app.log | jq .

10.4 Metrics

GET /api/metrics answers the operational questions directly: how many jobs exist and in what states, what fraction of them failed, how long an average row takes to process, how long an average job takes, and how many rows have been processed in total. Administrators see the whole system; ordinary users see their own jobs. The Administration page renders all of it.

11 · Security posture

What is defended, and how.

11.1 Passwords and tokens

  • Passwords are hashed with bcrypt and a per-password salt. Plaintext is never stored and never logged. A test asserts the stored value is a bcrypt hash rather than the password.
  • bcrypt silently ignores anything past 72 bytes, which would quietly weaken a long passphrase. The code truncates deliberately at that boundary rather than pretending the tail counted.
  • Sessions are stateless JWTs signed with HS256, carrying the user id and role, with an expiry that is enforced. A token belonging to a deleted user is rejected — proven by a test.

11.2 Tenant isolation

Every query for a job, a row or a report is scoped by user_id. Administrators are the single, explicit exception.

Requesting another user's job returns 404, not 403. A 403 confirms the resource exists, which lets an attacker enumerate valid job IDs. A 404 reveals nothing. The cost is marginally less helpful feedback to a legitimate user who mistyped a URL — a trade worth making. Every ownership-sensitive endpoint has a test asserting this.

11.3 Upload safety

RiskMitigation
Path traversal via filenameThe client's filename is never used as a path. Files are stored under a server-generated UUID; the original name is kept as data only.
Disk exhaustionThe size cap is enforced while streaming to disk, and the partial file is deleted the moment the limit is crossed.
Upload floodingA per-user token-bucket limiter returns 429 with a Retry-After header.
Unexpected file typesAn extension allow-list, checked before anything is written.
Malicious content crashing the pipelineEvery parse and conversion is guarded; bad data becomes a flagged row, never an exception that escapes.

11.4 At the edges

  • CORS is restricted to a configured origin list rather than a wildcard.
  • Unhandled exceptions return a generic message — no tracebacks or internal paths reach the client.
  • The WebSocket validates its token before accepting the connection, and refuses with a 4401 close code. Browsers cannot set headers on a WebSocket handshake, so the token travels as a query parameter; this is noted because it means the token can appear in proxy logs, which is the known trade of that approach.
  • SQL is built entirely through SQLAlchemy's expression layer — no string-concatenated queries.

11.5 What production would still need

Stated plainly rather than glossed over: a real secret in JWT_SECRET (the default is a development placeholder and the application should refuse to start with it in production), HTTPS termination, refresh-token rotation, account lockout after repeated failed logins, and a rate limiter backed by shared storage rather than process memory.

13 · Design decisions & tradeoffs

Every one of these had a defensible alternative. What follows is the choice made and what it costs — because a decision stated without its price is not a decision, it is a preference.

SQLite rather than PostgreSQL

Chosen because it removes every setup step: clone, run two scripts, working dashboard. No daemon, no credentials, no container just to read a table.
It costs a single writer at a time, which shaped the concurrency model — and no network access to the database.
Escape hatch: change DATABASE_URL. Nothing else in the code assumes SQLite.

Threads rather than async or multiprocessing

Chosen because the per-row cost is I/O-shaped and the real work is short. Threads give genuine speedup without process-spawn cost, without pickling, and without rewriting the database layer as async.
It costs no benefit if the work ever becomes CPU-bound.
Escape hatch: swapping in ProcessPoolExecutor touches one module.

Jobs serialized, rows parallel

Chosen because SQLite permits one writer, so parallel jobs would contend rather than scale, while parallel rows deliver the concurrency the brief asks for.
It costs throughput when many users upload simultaneously — jobs queue behind each other.
Escape hatch: the queue interface is deliberately the same shape as a distributed broker's.

An in-process queue and event hub rather than Redis

Chosen because the brief asks for a self-contained system, and Redis means a service to install, run and explain.
It costs multi-process workers and durability across restarts.
Escape hatch: both sit behind narrow interfaces — JobQueue and EventHub — specifically so they can be replaced without touching the routers or the pipeline.

Duplicate detection outside the worker threads

Chosen because workers finish out of order, so detecting duplicates inside them would make "which row is the original" depend on thread scheduling. The same file could produce different reports on different runs.
It costs a little extra code and a serial pass over each completed batch.
What it buys: reproducible output, which for an analytics tool is non-negotiable.

Honouring both duplicate signals

Chosen because the brief's stated rule and the brief's own sample data disagree, and satisfying only the literal rule would fail the stated acceptance criteria.
It costs a genuine false-positive risk on identical-but-distinct sales.
Escape hatch: DUPLICATE_DETECTION=id. The conflict is documented rather than silently resolved.

Reports stored per metric family, not as one blob

Chosen because the brief's example query — revenue-by-region across recent jobs — then becomes one indexed join instead of deserialising every metric for every job.
It costs six small rows per job instead of one.
Bonus: re-aggregation becomes an upsert rather than a rewrite.

Invalid rows stored, not discarded

Chosen because the stored rows are the error report the brief asks for, and the annotated export is simply a dump of them.
It costs storage proportional to the bad data.
What it buys: a user can filter, search and export exactly what went wrong, with the original values preserved alongside the error codes.

404 rather than 403 for other users' resources

Chosen because a 403 confirms a resource exists, which enables ID enumeration.
It costs slightly less helpful feedback on a mistyped URL.

WebSockets with a polling fallback

Chosen because proxies and corporate networks drop WebSocket upgrades, and progress that silently stalls is worse than progress that updates slowly.
It costs two code paths to maintain instead of one.

A hand-written CSS design system rather than a UI kit

Chosen because four runtime dependencies total, full control over the result, and no framework idioms leaking into the markup.
It costs more up-front work than importing a component library.

A written specification before any code

Chosen because it is what made parallel work safe — three streams could proceed at once against pinned contracts, and integration was running the suite rather than rewriting.
It costs time before the first line of implementation.

14 · How AI tools were used

The brief asks for an explanation of how AI tools were used to arrive at the solution. This section answers that honestly — including where the model was wrong and how that was caught.

14.1 The tool and the posture

The project was built with Claude Code (Opus) operating as the engineer of record under human direction — not as autocomplete, and not as an oracle. The working assumption throughout was that model output is a proposal which earns its place by passing a check, not by sounding plausible.

14.2 Specification before implementation

The first artefact was not code. The brief was turned into SPEC.md: validation rules with named error codes, the data model with the reasoning for each index, the complete API surface, and numeric acceptance criteria for the sample file. Everything afterwards was built against that document rather than against a fading memory of a PDF.

This had a concrete payoff beyond tidiness — it is what made the next step safe.

14.3 Parallel agents against pinned contracts

Once the foundation existed — settings, models, schemas, security, logging — and the module interfaces were pinned down to exact function signatures, the work was split across three concurrent streams:

StreamScope
Processing agentValidation, metrics, the worker pool, the queue, the event hub, and their unit tests.
Frontend agentThe entire React application, built against the API contract in the specification.
Main sessionThe API layer, integration tests, review, verification and this document.

Precise contracts are what made the three streams composable. When they met, integration was a matter of running the suite — not of rewriting interfaces that had drifted. Each agent was given an explicit scope boundary and told not to commit, so the work could be reviewed before it landed.

14.4 Where the model was wrong — and how it was caught

This is the part worth reading. Three substantive errors surfaced, all caught by verification rather than by inspection:

What went wrongHow it surfacedResolution
A real bug. The rows endpoint tried to validate an ORM object whose errors column is JSON text, so every row query failed. Integration tests failed the moment the two halves met. Decode the JSON before constructing the response model.
Bad arithmetic in the expected values. Hand-computed gross revenue and discount impact for the sample file were simply wrong. Tests failed — but the code was right and the test was wrong. Recomputed independently, confirmed the pipeline, corrected the expectations and the README.
A proposal that had to be refused. An agent, unable to reconcile the brief's duplicate rule with its sample data, proposed editing the sample file so its implementation would pass. Caught on review of the agent's report. Rejected — the sample data is the requirement, not a variable. The underlying contradiction was analysed and both duplicate signals implemented instead.
The third case is the instructive one. An agent reported a clean suite and a tidy explanation for why the brief's own acceptance numbers could not be met. Taking that at face value would have produced a system that passed its own tests while failing the actual requirement. Delegation does not transfer accountability.

14.5 Verification, not assertion

Every claim in this handbook is backed by something that can be re-run:

  • 138 automated tests covering each validation rule, the hand-computed figures, tenant isolation on every endpoint, retry exhaustion, rate limiting, WebSocket event ordering, and a full 10,000-row run.
  • A measured concurrency assertion with a hard wall-clock bound, so a silent regression to sequential processing fails the build.
  • Real browser verification — the UI was driven end to end against the real backend, with live WebSocket frames observed on the wire, not assumed from a clean compile.
  • A clean-clone rebuild — the repository was cloned fresh and set up from scratch to confirm the instructions in this document actually work.

14.6 Where human judgment stayed in charge

The stack choice, the two-level concurrency model, the decision to detect duplicates outside the worker threads, returning 404 instead of 403, the reading of the duplicate-rule contradiction, and the line between what to build and what to document as a limit — these were directed and reviewed, not generated. The model's first instinct was not always right, and the tradeoffs recorded in Section 13 are the ones that survived scrutiny.

14.7 The honest summary

AI tooling compressed the timeline substantially — particularly on breadth, where three workstreams advanced at once, and on the unglamorous mass of tests, types and documentation that usually gets cut first. It did not remove the need for engineering judgment. What it changed is where that judgment gets spent: less on typing, more on specifying precisely, reviewing sceptically, and insisting that every claim be checkable.

15 · Known limits & next steps

Stated plainly. A handover that only lists strengths is not a handover.

15.1 Current limits

LimitConsequence, and the workaround
Single processJob state lives in memory. A restart mid-job leaves that job showing processing. Re-triggering it is safe — processing is idempotent and clears prior rows first. A startup sweep that re-queues interrupted jobs would close this.
Rate limiting is per processBehind multiple instances the effective limit multiplies. Needs shared storage to be exact.
No database migrationsThe schema is created directly from the models. Fine for a greenfield database; Alembic would be required once there is data worth preserving.
Content-based duplicates can false-positiveTwo genuinely distinct but identical sales would be flagged. Configurable via DUPLICATE_DETECTION, and documented rather than hidden.
SQLite write throughputOne writer at a time caps concurrent job throughput. Moving to PostgreSQL is a connection-string change plus removing the job serialization.
WebSocket token in the query stringBrowsers cannot set headers on a WebSocket handshake, so the token may appear in proxy logs. A short-lived ticket exchanged for the socket would be the production fix.
The cross-job region report has no screen/api/reports/by-region is implemented and tested but surfaced only via the API; the dashboard shows cross-job totals instead.
No frontend unit testsThe UI is covered by type-checking, a production build and real-browser verification, but not by component tests.

15.2 What I would do next, in order

  1. Re-queue interrupted jobs on startup. Small change, removes the most visible rough edge.
  2. Refuse to boot with the default JWT_SECRET outside development. Cheap, and closes the most dangerous misconfiguration.
  3. Component tests for the dashboard. Vitest and Testing Library on the progress hook and the row explorer first — the two pieces with real logic.
  4. Alembic migrations. Before any deployment that keeps data.
  5. PostgreSQL plus a real broker. Only when concurrent job throughput actually becomes the constraint — both seams are already cut for it.
  6. Scheduled recurring reports. The brief lists this as optional; the aggregation path is already separate and callable, so it is mostly a scheduler and an email template.

Appendix B · Troubleshooting

SymptomCause and fix
The footer says the API is unreachable The backend is not running or is on another port. Check curl localhost:8000/api/health. The dashboard proxies /api to port 8000 — see frontend/vite.config.ts.
setup.sh says ensurepip is unavailable Expected on Debian and Ubuntu, which split venv from ensurepip. The script detects this and bootstraps pip itself; the message is informational. If it still fails: sudo apt install python3-venv.
Port 8000 or 5173 already in use lsof -ti:8000 | xargs kill, or pass --port to uvicorn and Vite.
A job is stuck in processing Almost certainly the API restarted mid-job (see Section 15.1). Press Re-process — it is idempotent and clears the previous rows first.
The progress bar says "polling" rather than "live" Working as designed. The WebSocket could not be established, so it fell back to polling. Progress is still accurate, just updated every two seconds.
Uploads return 429 The per-user rate limit. Wait for the Retry-After interval, or raise UPLOAD_RATE_LIMIT.
A job failed immediately The file could not be parsed at all — empty, no header, or invalid JSON. The job's error message says which. The job detail page shows it.
More duplicates than expected Content-based detection is on by default (Section 7.2). Set DUPLICATE_DETECTION=id for strict ID-only matching.
The Administration page refuses me Only the first registered account is an administrator. Promote another account by setting its role to admin in the users table.
Tests fail on a slow or loaded machine The concurrency test asserts a wall-clock bound. Run ./scripts/test.sh without --slow to skip timing-sensitive tests.
I want to start completely fresh rm -rf backend/data backend/logs — the schema and directories are recreated on the next start. This deletes all accounts and jobs.
